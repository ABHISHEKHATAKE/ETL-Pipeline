# Interview notes for this project

## 30-second pitch
"I built a batch ETL pipeline for retail orders. Raw CSVs are extracted, cleaned with Pandas, and run through eight validation rules. Bad rows go to an audit table with a reason code, good rows are loaded into a PostgreSQL star schema. Airflow orchestrates it daily. The load is idempotent and runs in one transaction, so retries and re-runs never create duplicates or half-loaded data."

## Questions you should be ready for

**Why a star schema?** Analytics queries are mostly aggregations over measures sliced by dimensions (date, customer, product). A star schema keeps joins shallow and queries simple and fast. It is denormalised on purpose (OLAP), unlike the normalised OLTP source.

**What is the grain of the fact table?** One order line. `(order_id, order_line)` is unique.

**How is the load idempotent?** Dimensions use `INSERT ... ON CONFLICT (business_key) DO UPDATE`; the fact table uses `ON CONFLICT (order_id, order_line) DO UPDATE`. Same input twice gives the same final state. I tested it: the second run added 0 rows.

**What if the DAG fails halfway?** Extract/transform/validate only write files in staging, so nothing in the warehouse changes. The load is a single transaction, so it either fully commits or fully rolls back. The failed run is logged in `etl_run_log` and Airflow retries it.

**What happens with bad data?** Fixable problems are repaired (whitespace, casing, bad email nulled). Unfixable rows are rejected with a reason and saved with their original values. If more than 20% of rows are rejected the whole run fails before loading, because that signals a broken source rather than a few bad rows.

**Why not pass data through XCom?** XCom is for small metadata. Large DataFrames go through files (parquet) so the metadata database isn't overloaded and tasks stay independent and restartable.

**ETL vs ELT?** This is ETL: transform happens in Python before loading. With a cloud warehouse (BigQuery, Snowflake, Redshift) you would usually load raw data first and transform with SQL/dbt (ELT).

**Batch vs streaming?** This is batch (daily). At ADP I used Kafka for event-driven processing, which is the streaming side. Batch is simpler and enough when data freshness of hours is acceptable.

**How would you scale it?** Read in chunks or switch the transform to PySpark; partition the fact table by month; add incremental loads using a high-water mark so each run only processes new files; use COPY instead of batched INSERTs for faster loading.

**What is SCD type 1 vs 2?** Type 1 overwrites old attribute values (what I do for customers). Type 2 keeps history by adding a new row with valid-from/valid-to dates. I'd add type 2 if the business needed "what city was the customer in when they ordered?".

**What would you improve?** Incremental loading, SCD type 2, declarative data-quality checks (Great Expectations), alerting on failures, and dbt for the SQL transformations.

## Be honest about
- The dataset is **synthetic** (generated by `etl/generate_data.py`), so the row counts and reject rate are from generated data with problems I injected on purpose. Say so if asked.
- You can run it on a real public dataset (for example an e-commerce orders CSV from Kaggle) by mapping its columns to the raw schema, then re-quote the numbers from that run.
